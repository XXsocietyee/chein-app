# Planning-requirements audit 2026-11-28: are the planned functions built, and are they closed loops?

Owner question: "Are all the functions implemented correctly? Refer to our documentation and the mini-program. Are they all closed loops?"

**Answer: No.** Most planned player and club features now exist as screens. The request bodies usually match the backend. But in Release most of them cannot complete their loop. The cause is almost never a missing screen. It is the Release composition, which never switches the screen's service on:
- nil approvals or leases;
- empty grant lists (`approvals: []`, `devices: []`, `artworkHosts: []`);
- services built with `gates: .disabled` or `service: nil`;
- path allow-lists that leave the route out, or refuse it outright (`MPFirstClubWriteRoute`, `playPaths`, the "registration"/"settlement" substring guards, and literal matching of templated paths in `RuntimeDependencyTransport.send`).

Of 133 open loops, the clear majority break at that composition step, before any request is sent.

**Method.** The requirement lines were consolidated into feature requirements in 7 domains: roam, team + registration, journey/play, club, social (posts/IM/share/feedback), mine (orders/money/me), and home/search/publish.

Each requirement was traced through every link of the loop:
1. the entry point from the tab roots (`SessionRootView`);
2. the coordinator and service;
3. the Release composition (`ReviewedPlayerWriteLeases.sessionDependencies`, `AppCompositionRoot`, `AppSession`, `MPFirstClubApprovals`, xcconfig, flags);
4. the HTTP method and fields, compared with the backend controller/DTO;
5. the result handling (success / empty / error / signed-out);
6. the state written back to related screens;
7. the MP page's behaviour.

This is static reading: the app was not built or run (there is no Swift toolchain in the cloud). Where a verdict contradicts the function audit, the code line is given. The most important ones were re-checked by hand (see "Corrections").

Older docs describe the earlier Flutter app, so each was judged on the feature, not the old file path. D3 ("stay on Flutter") is superseded by the SwiftUI app itself.
